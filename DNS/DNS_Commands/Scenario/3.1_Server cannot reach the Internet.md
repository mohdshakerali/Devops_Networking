
# Real-time DevOps scenario: "Server cannot reach the Internet"

Imagine you have a Linux server running an application:

```text
Application
     ↓
Linux Server
     ↓
Network
     ↓
Internet
```

Suddenly the application team says:

> **"The server can't download a package / can't connect to an external API."**

For example, the application needs to call:

```text
https://api.example.com
```

but it's failing.

You are the DevOps engineer. You need to find **where the problem is**.

You don't randomly run commands. You troubleshoot from the bottom upward.

---

# Step 1 — Check the server's IP/interface

First:

```bash
ip addr
```

You're asking:

> **Does this server actually have a network interface with an IP address?**

Suppose you see:

```text
wlo1:
    inet 192.168.1.8/24
    state UP
```

You know:

```text
Interface → wlo1
IP        → 192.168.1.8
Status    → UP
```

So the server has an IP.

But **don't conclude that networking is working yet.**

An interface being `UP` doesn't guarantee connectivity.

---

# Step 2 — Check where the server sends traffic

Now:

```bash
ip route
```

Suppose:

```text
default via 192.168.1.1 dev wlo1
192.168.1.0/24 dev wlo1
```

You're asking:

> **Does the server have a route to other networks?**

You see:

```text
default via 192.168.1.1
```

So the server knows:

> "For destinations outside my local network, send packets through `192.168.1.1`."

Good.

---

# Step 3 — Test the server itself

Now:

```bash
ping -c 4 127.0.0.1
```

You're asking:

> **Is the local networking stack working?**

If:

```text
4 received
0% packet loss
```

✅ Local networking is responding.

If this failed, there would be no point immediately blaming the Internet or DNS. You'd investigate the local machine/network stack first.

---

# Step 4 — Test the gateway

Next:

```bash
ping -c 4 192.168.1.1
```

You're asking:

> **Can my server reach its gateway?**

If it succeeds:

```text
4 received
0% packet loss
```

Then:

```text
Server
192.168.1.8
     ↓
     ↓ ✅
     ↓
Gateway
192.168.1.1
```

So your local network path to the gateway works.

If it fails:

```text
Server
192.168.1.8
     ↓
     ✕
     ↓
Gateway
192.168.1.1
```

Then you investigate things like:

* Wi-Fi/Ethernet connection
* interface configuration
* VLAN/network configuration
* gateway availability
* firewall/network policy

You **don't jump to DNS yet**.

---

# Step 5 — Test an external IP

Now:

```bash
ping -4 -c 4 8.8.8.8
```

You're asking:

> **Can I reach an external IP address?**

Suppose:

```text
4 transmitted
4 received
0% packet loss
```

Then:

```text
Server
   ↓ ✅
Gateway
   ↓ ✅
External network
   ↓ ✅
8.8.8.8
```

This tells you that basic external IP connectivity is working.

---

# Step 6 — Test DNS

Now suppose the application is trying to reach:

```text
api.example.com
```

You test:

```bash
dig api.example.com
```

You're asking:

> **Can DNS resolve this hostname to an IP address?**

Suppose:

```text
api.example.com.    A    203.0.113.50
```

DNS works.

If instead you get something like:

```text
SERVFAIL
```

or:

```text
connection timed out
```

then you have a DNS problem to investigate.

---

# So this is the actual troubleshooting thought process

When someone says:

> **"The application can't connect to the server/API."**

You can think:

```text
             APPLICATION FAILURE
                    │
                    ↓
        Does the machine have an IP?
                    │
                 ip addr
                    │
                    ↓
          Does it have a route?
                    │
                ip route
                    │
                    ↓
        Is local networking working?
                    │
           ping 127.0.0.1
                    │
                    ↓
          Can I reach my gateway?
                    │
           ping <gateway>
                    │
                    ↓
        Can I reach external IP?
                    │
            ping 8.8.8.8
                    │
                    ↓
             Is DNS working?
                    │
              dig domain
                    │
                    ↓
       Then test the actual service
                    │
                  curl
```

**This is the important part.**

The commands are not separate topics.

They form a **troubleshooting chain**.

# And here's a very realistic example

Suppose tomorrow your manager says:

> "Our server cannot access `api.company.com`."

You SSH into the server.

### You run:

```bash
ip addr
```

✅ Server has:

```text
192.168.1.8
```

Then:

```bash
ip route
```

✅ Default route exists.

Then:

```bash
ping -c 4 127.0.0.1
```

✅ Works.

Then:

```bash
ping -c 4 192.168.1.1
```

✅ Works.

Then:

```bash
ping -4 -c 4 8.8.8.8
```

✅ Works.

Then:

```bash
dig api.company.com
```

❌ DNS fails.

Now you've narrowed the problem down dramatically.

You can tell the team:

> **"The server has an IP, has a default route, can reach its gateway, and has external IP connectivity. The failure is occurring at DNS resolution for `api.company.com`."**

That's **real DevOps troubleshooting**.

## One correction to your understanding

You said:

> "first check the ip addr then find out the loop then ping it"

Almost. 👍

You **don't normally find the loop and then ping it every time**.

Think of the commands as **layers of diagnosis**.

```text
ip addr
   ↓
"Do I have an IP/interface?"

ip route
   ↓
"Do I know where to send traffic?"

ping gateway
   ↓
"Can I reach my local network?"

ping external IP
   ↓
"Can I reach outside?"

dig
   ↓
"Can DNS resolve names?"

curl
   ↓
"Can the actual application/service be reached?"
```

`127.0.0.1` is useful as a **local-stack isolation test**, especially when troubleshooting something on the machine itself. It isn't necessarily the first command you run for every incident.

### 🔥 The DevOps mindset

Don't memorize:

> "`ping` means connectivity."

Instead think:

> **"What exact part of the connection am I trying to prove?"**

That's what makes these commands useful.
