# DNS — Let's REALLY understand it

Forget the words **resolver, authoritative, recursive, root** for a moment.

Imagine you are sitting at your Linux server.

You run:

```bash
curl https://api.example.com
```

You understand `curl` is trying to communicate with a server.

But there is a problem.

Your server knows:

```text
api.example.com
```

but networking ultimately needs an IP address such as:

```text
203.0.113.50
```

So the first question is:

> **"Who can tell my server the IP address of `api.example.com`?"**

That's the problem DNS solves.

---

# 1. Your application doesn't know the IP

Let's say your application has this configuration:

```text
DATABASE_HOST=db.company.com
```

The application wants to connect to:

```text
db.company.com
```

It doesn't necessarily know:

```text
10.20.30.40
```

So the application asks the operating system:

> "Please resolve `db.company.com`."

Think of it like this:

```text
Application
     |
     | "What is the IP of db.company.com?"
     ↓
Linux
```

Now Linux needs to figure it out.

---

# 2. Linux doesn't ask the entire Internet randomly

This is where DNS configuration comes in.

Your Linux machine has been configured with information about **which DNS resolver it should use**.

For example, conceptually:

```text
Linux Server
     |
     | DNS query
     ↓
DNS Resolver
```

The resolver could be:

```text
8.8.8.8
```

or:

```text
1.1.1.1
```

or, in a company:

```text
10.0.0.10
```

or in a cloud environment, an internal cloud-provided DNS resolver.

So the first important relationship is:

> **Your application asks Linux → Linux asks its configured resolver.**

---

# 3. Now imagine the resolver receives this question

Your server says:

```text
"Hey resolver, what is the IP of api.example.com?"
```

The resolver has two possibilities.

### Possibility A — It already knows

Maybe another machine asked the same question 30 seconds ago.

The resolver has cached:

```text
api.example.com → 203.0.113.50
```

So it can immediately respond:

```text
"Here you go:
203.0.113.50"
```

That's it.

No further DNS journey is required.

---

# 4. But what if the resolver doesn't know?

This is where DNS becomes interesting.

Suppose the resolver's cache is empty.

It receives:

```text
api.example.com
```

and thinks:

> "I don't know the answer. But I know how to find it."

This is the key idea behind a **recursive resolver**.

Your server doesn't have to understand the whole DNS hierarchy.

It simply asks the resolver:

```text
"Find the answer for me."
```

The resolver takes responsibility for finding the answer.

That's why it's called **recursive**.

---

# 5. Now the resolver starts looking

The resolver needs to discover:

> "Who is responsible for `api.example.com`?"

DNS is organized like a hierarchy.

Take:

```text
api.example.com
```

Break it apart:

```text
api
example
com
.
```

The `.` at the end is important.

It represents the **root of DNS**.

So conceptually:

```text
.
└── com
    └── example
        └── api
```

Don't worry about `api` yet. We'll get there.

---

# 6. First: the Root

The resolver can ask a **root DNS server**:

> "I need information about `api.example.com`."

The root doesn't normally say:

```text
api.example.com = 203.0.113.50
```

Why?

Because the root isn't responsible for the individual `example.com` domain.

The root's job is higher up.

It knows who handles the `.com` part.

So the root essentially tells the resolver:

> "For `.com`, go talk to the `.com` DNS servers."

Conceptually:

```text
Resolver
   |
   | "Where do I find example.com?"
   ↓
Root
   |
   | "Ask .com"
   ↓
.com DNS
```

---

# 7. Now the resolver talks to `.com`

The resolver asks:

> "Who is responsible for `example.com`?"

The `.com` DNS servers don't necessarily know:

```text
api.example.com → 203.0.113.50
```

Instead, they know:

> "These DNS servers are authoritative for `example.com`."

So they point the resolver toward the **authoritative DNS servers for `example.com`**.

For example, conceptually:

```text
.com
   |
   | example.com is handled by:
   ↓
ns1.example-dns.com
ns2.example-dns.com
```

Now the resolver knows where to ask next.

---

# 8. Now we reach the important guy: Authoritative DNS

The resolver goes to the authoritative DNS server.

And asks:

```text
"What is api.example.com?"
```

This server is different from the resolver.

Why?

Because this server is responsible for the DNS records for the domain.

Imagine the company has configured:

```text
api.example.com → 203.0.113.50
db.example.com  → 10.20.30.40
www.example.com → 203.0.113.60
```

The authoritative DNS server has those records.

So it can answer:

```text
api.example.com
        ↓
203.0.113.50
```

**Now we finally have the answer.**

---

# 9. The answer travels back

The authoritative server gives the answer to the resolver:

```text
api.example.com
       ↓
203.0.113.50
```

The resolver then gives it back to your Linux machine.

```text
Authoritative DNS
       ↓
Resolver
       ↓
Linux
       ↓
Application
```

And now your application knows:

```text
api.example.com
       ↓
203.0.113.50
```

Only **after this** can your application attempt the actual connection.

---

# 10. This is the complete story

Let's put everything together.

You run:

```bash
curl https://api.example.com
```

### Step 1

Application says:

```text
"I need api.example.com"
```

### Step 2

Linux needs to resolve it.

```text
Linux
 ↓
Configured DNS resolver
```

### Step 3

Resolver checks its cache.

```text
Is api.example.com already cached?
```

If yes:

```text
CACHE
 ↓
203.0.113.50
```

Done.

If no:

```text
Resolver
 ↓
Root
 ↓
.com
 ↓
Authoritative DNS
 ↓
203.0.113.50
```

Then:

```text
203.0.113.50
 ↓
Linux
 ↓
Application
```

Now the application can continue with the actual connection.

---

# 🔥 Now let's understand Resolver vs Authoritative properly

This is where my previous explanation was too shallow.

Imagine you call a company's receptionist and ask:

> "What is the phone number of the CEO?"

The receptionist may not personally own the CEO's phone.

But she knows how to find it.

That's similar to the **resolver**.

The authoritative source is the place that actually maintains the official information.

So:

### Resolver

Your server asks:

> "Find me the answer."

Resolver says:

> "Sure, I'll find it."

It might:

* check its cache
* ask root
* ask TLD
* ask authoritative DNS
* return the answer

### Authoritative DNS

The resolver asks:

> "What is the official DNS information for this domain?"

Authoritative DNS says:

> "Here are the records configured for my domain."

---

# ⭐ This distinction matters A LOT in DevOps

Imagine you change:

```text
api.company.com
```

from:

```text
10.10.10.10
```

to:

```text
10.10.20.20
```

You change it at the **authoritative DNS**.

But suddenly you might check from your server and still see:

```text
10.10.10.10
```

Why?

Because your resolver may have the old answer **cached**.

That's where **TTL** becomes important.

We'll learn TTL properly later.

This is one reason someone says:

> "I changed DNS, but I'm still getting the old IP."

It doesn't necessarily mean your DNS change failed.

---

# 🔥 Another important DevOps scenario

Imagine:

```text
Developer laptop
      ↓
DNS works
      ↓
api.company.com → 10.20.30.40
```

But production server:

```text
Production server
      ↓
DNS fails
      ↓
"Could not resolve host"
```

You should NOT immediately conclude:

> "The API server is down."

The application may never have reached the API server.

The failure could be:

```text
Application
    ↓
DNS resolution ❌
    ↓
No IP
    ↓
No connection attempt
```

This is exactly why DNS knowledge matters in DevOps.

---

# 🧠 One more thing: DNS doesn't only give IP addresses

This is another place where beginner explanations can create problems.

DNS is not simply:

```text
Name → IP
```

DNS is a **system of records**.

For example:

```text
A       → IPv4 address
AAAA    → IPv6 address
CNAME   → another hostname
MX      → mail server
NS      → authoritative DNS server
TXT     → text information
PTR     → reverse DNS
```

We'll learn these **one by one**, with real DevOps examples.

Don't memorize them yet.
